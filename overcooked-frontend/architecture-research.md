## 研究問題與結論

1. **RAG 可沿用既有 PostgreSQL。** pgvector 可儲存向量並進行相似度查詢；使用者已另行核准 PostgreSQL＋pgvector，OpenAI 負責向量化與生成。具體模型、檢索評分與資料集尚未核准。
2. **已有可開始整理的中文食譜來源。** HowToCook 為具明確授權的候選；仍需人工整理食材別名、用量、步驟與來源版本，不能直接把網頁文字當可計算資料。
3. **包裝零售價格仍須驗證接入。** 找到公開 API 候選，但尚無證據證明能覆蓋本案所有生鮮食材與包裝量，也未驗證零售商原始授權 feed。
4. **營養計算不能用一張通用係數表處理所有食材與烹調方式。** 每 100 g 可食部、生熟狀態、烹調產率與營養保留需分開處理。核心熱量／蛋白質缺少依據時，仍遵守已核准的禁止採用規則。
5. **增肌／減脂參數仍需決策。** 可找到成人能量與蛋白質的候選依據，不能把單一運動族群的研究結果直接套用全部家庭成員。

## 一、RAG、模型與費用

### 已查證

- pgvector 是 PostgreSQL 擴充，支援餘弦等距離；預設精確近鄰搜尋，可結合其他篩選與文字檢索。小型食譜集不必立即使用近似索引。[官方 repository](https://github.com/pgvector/pgvector)
- OpenAI GPT-5 mini 支援 Structured Outputs；查證時官方列出的每百萬 token 價格為輸入 USD 0.25、輸出 USD 2.00。這只是可評測的低成本候選，尚未指定為最終生成模型。[模型文件](https://developers.openai.com/api/docs/models/gpt-5-mini)
- text-embedding-3-small 查證時官方價格為每百萬輸入 token USD 0.02，作為向量化候選。[模型文件](https://developers.openai.com/api/docs/models/text-embedding-3-small)
- Structured Outputs 可約束結構，但內容仍可能出錯；拒答與不完整輸出需獨立處理，不能把 JSON 格式有效視為價格、營養、食材或烹調方法正確。[官方指南](https://developers.openai.com/api/docs/guides/structured-outputs)
- OpenAI File Search 是另外的託管檢索方案，需要建立 vector store 並上傳文件。本次使用者已選擇自行以 PostgreSQL＋pgvector 管理食譜，無須再將它設為必備服務。[官方 File Search 指南](https://developers.openai.com/api/docs/guides/tools-file-search)

### 查證時的候選設計（現行決策見已核准架構）

- 每筆食譜先保留結構化食材、用量、步驟、來源、授權與原始版本，再產生可檢索文字及向量；向量結果只用來挑候選。
- 指定菜色、食材 ID／別名及過敏限制需有明確比對，不讓語意相似度取代必要條件。
- 生成輸出只允許引用這次實際檢索到的來源 ID；無檢索直接生成另記模式，不能自行捏造來源。
- 使用者文字與檢索內容是資料，不是可覆寫系統規則的指令；模型不直接寫入採用狀態。
- 模型費用按實際回傳 usage 計帳，呼叫前原子預留上限，包含重試與背景工作；外部服務總額另計主機及資料費用。供應商提醒不可直接當成本案每月 NT$2,000 的完整硬上限。
- 示意成本：若單次輸入 8,000 token、計費輸出共 4,000 token，依上述價格為 USD 0.01；1,000 次為 USD 10，另加向量化、其他服務、匯率／稅費及失敗重試。這是算術情境，不是延遲、品質或實際用量保證；推理模型的輸出預算也要包含計費推理 token。

資料可行性檢查須涵蓋品名、原料狀態、淨重、包數、價格、時間、地區、庫存、優惠條件與來源。未知淨重的商品不能直接進比例成本計算。

已核准的同規格單包計算，可表達為：

```text
缺量 = 0（已確認為家中已有的種類，視為足量）
缺量 = 整餐需求量（未列為已有的種類）
採購價 = ceil(缺量 / 每包量) × 單包價
成本價 = 缺量 / 每包量 × 單包價
```

需購食材的需求量與包裝量須轉為相同重量基準；使用者不提供庫存重量。去皮、帶骨、組合包、不同單位及多件優惠不能未經處理直接套公式。價格由後端取得，前端只顯示缺少種類的雙價格與合計。已有種類成本為 0，但仍按配方用量計營養；查無價格則保留缺值，不能填 0，採用例外仍依 Spec。

## 四、營養目標與烹調估算

### 目標公式的候選依據

- 國健署 DRIs 第八版的說明列成人蛋白質建議量 1.1 g/kg/day，可作一般維持模式的候選基準，不等於增肌處方。[國健署說明](https://health99.hpa.gov.tw/storage/files/themes/%E3%80%8C%E5%9C%8B%E4%BA%BA%E8%86%B3%E9%A3%9F%E7%87%9F%E9%A4%8A%E7%B4%A0%E5%8F%83%E8%80%83%E6%94%9D%E5%8F%96%E9%87%8F%E3%80%8D%E7%AC%AC%E5%85%AB%E7%89%88_%E7%B7%9A%E4%B8%8A%E8%AA%AA%E6%98%8E%E6%9C%83%E4%B9%8B%E9%87%8D%E9%BB%9E%E7%B4%80%E8%A6%81.pdf)
- 國健署提供依體重狀態與活動程度的每日飲食建議表，為簡單能量估算的候選。例：正常體重且輕度工作列 30 kcal/kg/day。不得把其中一格套用到所有成人。[官方資料](https://www.hpa.gov.tw/Pages/Detail.aspx?nodeid=544&pid=728&sid=725)
- Mifflin 原始研究提出成人靜息能量公式：男性 `10W + 6.25H - 5A + 5`，女性 `10W + 6.25H - 5A - 161`，W 公斤、H 公分、A 歲。研究包含 19–78 歲健康成人；靜息能量不是每日總消耗，活動換算仍需另有依據。[原始研究](https://pubmed.ncbi.nlm.nih.gov/2305711/)
- 增肌／減脂研究有特定運動與族群條件，不能直接選一組倍率宣稱適用全部家庭成員。例如 Longland 的高蛋白減脂試驗屬年輕男性及密集運動條件；能量盈餘研究也不能支持越多盈餘就越多肌肉。[減脂 RCT](https://pubmed.ncbi.nlm.nih.gov/26817506/)、[盈餘原始研究](https://pmc.ncbi.nlm.nih.gov/articles/PMC10620361/)
- 一般健康成人的產品適用範圍仍須在架構中明確化。NIH Body Weight Planner 本身限制成人，並排除孕期及哺乳期；這不是本案已核准新增的詢問欄位，只是適用性設計的參考。[官方工具](https://www.niddk.nih.gov/health-information/weight-management/body-weight-planner)

以上不是本專案已選公式，也不是提供使用者個人飲食處方；增肌／減脂調整係數、適用族群及版本化規則仍待具體方案與核准。

### 食材、重量與烹調

- TFDA 成分值以每 100 g 可食部為基準，不能直接用包裝毛重計營養；以原料型樣品為主，也不能假定每個食材都有對應熟食條目。[TFDA 官方研究，頁 3–4](https://www.fda.gov.tw/tc/includes/GetFile.ashx?id=f637744876252406610)
- USDA Retention Factors Release 6 涵蓋維生素、礦物質及酒精共 26 項，**不是熱量與蛋白質的通用保留係數表**。[官方資料說明](https://www.ars.usda.gov/northeast-area/beltsville-md-bhnrc/beltsville-human-nutrition-research-center/methods-and-application-of-food-composition-laboratory/mafcl-site-pages/nutrient-retention-factors/)
- USDA 肉類／禽類烹調產率資料對應特定食材、部位及方法；重量、水分與脂肪變化不代表所有營養素同比例損失，部分資料也不完整。[原始產率資料](https://www.ars.usda.gov/ARSUserFiles/80400535/Data/retn/USDA_CookingYields_MeatPoultry02.pdf)

候選運算路徑：

1. 優先使用可核對的「相同食材＋相同烹調狀態」成分資料及對應熟可食重量；已用熟食資料就不再套一次烹調修正。
2. 只有生食資料時，須有適用的可食部、產率與必要營養轉換依據。加入的油、醬料，以及保留或倒掉的湯汁需有資料表示。
3. 保存購入重量、生可食重量、熟可食重量、狀態、營養樣品 ID、轉換來源／版本，避免重複扣除去皮或失水。
4. 關鍵營養值／食材對映／必要烹調轉換缺失時，保留「營養未完整」，不能預設 0 或任意當作 100% 保留後標成已驗證。

### 架構歧義與後續決定

- 先前提出 `1n` 用於初始份量、最終回到未縮放營養目標的建議未被採用。使用者後續明確決定：先對齊基準食譜的熱量／蛋白質，再將份量及最終營養驗證目標同步乘 n。系統須明確區分基準目標與食量調整後的規劃目標；後者是使用者指定的產品規則，不宣稱 n 倍本身為醫學公式。
- 未成年人只有一般份量規劃時，如何加入全家營養目標尚需明確計算規則。
- 全家合計熱量／蛋白質通過 ±10% 不表示每位成員實際食用後都達標；本案顯示合計食譜，應表達為整餐估算符合規劃目標。
- 固定配方等比例縮放不會改變蛋白質與熱量的比例，因此不保證一定能同時通過兩項容差。需設計候選更換或有邊界的配方調整，失敗時回傳無可行方案。

## 五、執行與驗證的技術證據

- APScheduler 3.x FAQ 明確提醒多程序共享 job store 的限制。若採 3.x，候選為單一排程程序，避免每個 API worker 各自啟動相同排程；不混用未確認的不同主版本文件。[官方 FAQ](https://apscheduler.readthedocs.io/en/3.x/faq.html)
- PostgreSQL 的 `SKIP LOCKED` 可用於佇列式資料表，但不是一般查詢的一致性解法。若以 DB 持久化生成工作，仍需自行設計租約、重試及冪等，不能只加鎖就宣稱可靠。[官方 SELECT 文件](https://www.postgresql.org/docs/14/sql-select.html)
- YOLO 驗證工具提供 precision、recall、mAP 等指標；本案「辨識 80%」需固定配對規則與測試集，不能以人工修正後結果或訓練集命中率代替。[Ultralytics 驗證文件](https://docs.ultralytics.com/modes/val/)

## 八、營養目標候選的補充證據

- ISSN 的蛋白質與運動立場文件對運動族群提出約 1.4–2.0 g/kg/day 的範圍；其適用條件是運動者，不能把選擇「增肌」或「減脂」本身視為已滿足運動條件，也不能把區間任一值當成官方唯一預設。[學會原文](https://link.springer.com/article/10.1186/s12970-017-0177-8)
- 國健署每日飲食建議表結合活動程度與體重狀態，包含調整至健康體重的目的。若採用該表，不應未經設計再疊加一層相同目的的增減倍率，避免重複調整。[國健署原文](https://www.hpa.gov.tw/Pages/Detail.aspx?nodeid=544&pid=728&sid=726)
- 後續已確認 n 倍用法：基準食譜先通過 ±10%，再同步縮放食譜份量與最終目標。成員 n 僅可選 0.7／0.85／1／1.15／1.3；基準 600 大卡／30 g 蛋白質在 1.3n 下，最終規劃目標為 780 大卡／39 g 蛋白質。此例為縮放算術，不是特定成人的每日營養建議。
