## 2. 設計原則

1. **物件就是入口。** 使用者點的是鍋、書、冰箱、畫，不是按鈕卡片。每個入口在房子裡有固定位置，換頁＝鏡頭移動到那裡。
2. **景深表達層級。** 越可操作的東西越靠近鏡頭。資料本身（數字、表格、表單欄位）永遠是平的、不傾斜，只有承載它的物件在動。
3. **未知不是零。** 營養缺值、價格未知、缺克重一律虛線框＋「未知」，不畫成 0、不填進進度條、不畫食物。
4. **後端狀態是真的。** 鍋蓋旁的階段只反映工作 API 回報的狀態，不做假百分比。鍋裡的食物是進度示意，不代表實際生成的菜。
5. **一眼可判斷。** 熱量 ≤110%、蛋白質 ≥90% 單邊檢查，用「通過／超出／計算不完整」三態，不用模糊顏色。
6. **整包花費 ≠ 按比例成本。** 兩個金額分兩行、各自標名。
7. **歷史快照只讀。** 從冰箱回看的餐單不可改、不可重算。

### 3.2 景深層級

每個房間固定五層；視差係數＝該層跟隨指標位移的比例。

| 層 | 視差係數 | translateZ | 用於 |
|---|---|---|---|
| `z0` 牆 | 0.15 | -120px | 磁磚、壁紙、窗景、門口 |
| `z1` 家具 | 0.40 | -40px | 沙發、流理台、餐桌面、冰箱門、畫框 |
| `z2` 物件 | 0.70 | 0 | 鍋、書、單板、盤子、便利貼、畫中人物 |
| `z3` 互動層 | 0.85 | 40px | 抬起的盤子、翻出的菜色卡、展開的收據 |
| `z4` 浮動 | 1.00 | 80px | 吉祥物、對話面板、Toast、底部分頁 |

- 陰影暖棕 `rgba(90,50,20,α)`；層越高越大越淡。
- 可互動物件 hover 時上浮到 `z3` 並加亮邊，觸控裝置以輕微放大代替。
- 傾斜上限：物件 ±8°、場景整體 ±4–6°；文字層不旋轉。

### 3.5 寫實畫風規範

場景（房間分層 SVG）一律寫實；吉祥物與全家福裡的蠟筆人物是刻意的例外。

| 項目 | 規則 |
|---|---|
| 光源 | 每個場景一個主光（大門：右後方的夕陽＋壁燈；室內：吊燈或窗光），所有高光、陰影方向一致 |
| 材質 | 木紋、牆面、石材、布料、陶、金屬各有紋理；以 `feTurbulence` 雜訊疊在漸層底色上，牆面等大面積的雜訊不透明度 ≤ 0.2 |
| 立體 | 物件有圓柱／球面漸層、邊緣高光、落地陰影（模糊橢圓）；凹凸面依光源畫亮邊與暗邊 |
| 景深 | `z0` 遠景偏冷、降飽和、輕微模糊（大氣透視）；`z3` 前景失焦並壓暗；可加散景光斑與暗角 |
| 色彩 | 沿用 3.1 的色相，但場景內降低飽和、加入環境色（黃昏偏紫的陰影、暖色受光）；UI 元件仍用 3.1 tokens |
| UI 疊層 | 場景上的 UI（名牌卡、單板、收據、便利貼）是實體物件，照寫實畫法；浮動 UI（聊天室、Toast、分頁）是乾淨的奶油色面板，不加材質 |
| 圓角 | 場景內實體物件圓角小（紙卡 4–6px 等比）；浮動 UI 維持大圓角 |
| 限制 | 手寫 SVG 的半寫實程度，不是照片或 3D 算圖。濾鏡成本高：正式版每層在建置時轉成 WebP／AVIF（1x、2x），SVG 只作為原始檔 |

### 3.6 景深效果設定

| 模式 | 行為 |
|---|---|
| 沉浸（預設） | 完整場景、鏡頭隨指標／陀螺儀微調、鏡頭轉場、入鍋與蒸氣動畫 |

### 4.4 手機操作模型

房間是 16:10 的橫向長景，手機直式一次只看得到約三分之一寬。規則：**每一個可點物件，在手機上都必須不靠「碰巧滑到」就能操作到。**

| 機制 | 行為 |
|---|---|
| 停靠點（`stops`） | 每個房間定義 1–3 個鏡頭停靠點，每個停靠點保證該區的可點物件完整入鏡。左右滑動一次移動一個停靠點（不自由拖曳，避免停在半個物件上）。 |
| 停靠點指示 | 畫面頂端的點狀指示顯示目前在第幾個；左右邊緣有帶名稱的箭頭（例如「‹ 出菜口與食譜書」「冰箱 ›」），點了也會移動。 |
| 物件列（`HotspotDock`） | 底部分頁正上方一排膠囊按鈕，**列出這個房間所有可點物件與其狀態**（例如「左鍋 生成中」「單軌 3 張單」）。點一下：物件不在畫面內 → 鏡頭轉到它所在的停靠點並讓物件閃一下；已在畫面內 → 直接執行該物件的動作。目前停靠點內的物件以橘框標示。 |
| 層疊順序 | 由下而上：底部分頁、物件列、吉祥物跑道。聊天室視窗從吉祥物上方彈出。 |
| 陀螺儀 | 只做 ±4–6° 的微調視角，不負責換停靠點。 |
| 無障礙 | 物件列同時是鍵盤與讀屏使用的清單；桌機上以視覺隱藏的清單提供同一份內容，Tab 順序與物件列一致。 |

各房間的停靠點（實作值；fx＝停靠點中心在世界寬度的比例，span＝手機上一定要完整看到的寬度，單位是世界寬度 1600 的分量。
疊層座標比世界大一圈（1.06，見 7.3），所以畫稿座標 x 對應的 fx 是 `0.5 + (x/1600 − 0.5) × 1.06`；太靠邊的 fx 會被鏡頭夾回來）：

| 房間 | 停靠點（★＝預設） | 物件列 |
|---|---|---|
| 大門 | ★門 0.50（放大 1.2） | 無（只有登入卡） |
| 玄關 | ★門牌 0.375（span 680）／內門 0.78 | 每個家庭一顆、＋掛新門牌 |
| 客廳 | 沙發與窗 0.20／★電視牆 0.50／廚房門口 0.84 | 全家福、電視（狀態＝目前餐別）、廚房門口（狀態＝鍋） |
| 廚房 | 出菜口與食譜書 0.218（span 488）／★爐台 0.504（span 484）／冰箱 0.86（span 340） | 單軌（開「全部的單」面板）、食譜書、左鍋、空鍋（或第二口鍋）、兩張便利貼 |
| 食譜書 | ★左頁 0.302／右頁與托盤 0.698（都是 span 660） | 兩頁、托盤上的動作、翻頁、上一步、分類、闔上書等（依步驟而定） |
| 單板＋鍋 | ★鍋 0.681（span 700；問卷是下方抽屜） | 無 |
| 餐桌 | ★餐桌 0.50（span 900） | 每道菜、每位成員、家庭合計、收據、小知識；底部改為動作列 |
| 冰箱門 | ★已採用 0.2877（span 540）／營養與採購 0.668（span 576），兩個都貼齊上緣 | 月曆、當日餐單、一鍵購入（可以買的那幾餐）、拉開冰箱、趨勢圖、生成紀錄 |
| 全家福 | ★全家福 0.50（span 620） | 每位成員、＋新成員、全家名單、設定 |

客廳的廚房門口原訂 0.824，在 390×844 上門口離右緣只剩約 3 單位，所以改成 0.84。廚房三個停靠點加了 span，是為了讓單軌與鍋不被左右邊緣的「‹ ›」按鈕蓋住。
冰箱門上兩顆磁鐵本身就能換停靠點，邊緣按鈕移到磁鐵那一排（`edgeTop`），不蓋月曆。

寬螢幕比 16:10 扁（多數桌機瀏覽器視窗）時世界的上下會被裁掉；場景用 `useRoom().visible` 知道現在看得到畫稿的哪一塊，把東西留在裡面。

設計新房間時的檢查：把世界切成 0–35%、32–68%、65–100% 三段，任何可點物件都必須完整落在其中一段內；跨段的物件要移位或縮小。

**實作後的修正（2026-11-14）**：上面的三段是照審圖頁的 9:16 手機預覽（看得到約 560 單位寬）定的。實際的長螢幕手機（390×844）蓋滿畫面時只看得到約 **460 單位寬**，所以有些停靠點放不下（玄關的四張門牌、食譜書的一頁、餐桌、全家福的圖畫紙）。做法是停靠點可以指定 `span`（一定要看到的寬度）：鏡頭拉遠到看得全，世界變得比畫面矮並靠上放，下方留給物件列與分頁。玄關已經這樣做。其餘場景實作時要逐一檢查，並在審圖頁補一個 390×844 的預覽。

### 5.3 ②b 食譜書 `/pick`、`/pick/:id`

- **場景**：從正上方俯視流理台上攤開的綠色精裝書（和 ③ 是同一張檯面）。
- **分層**：`z0` 石紋檯面；`z1` 書（封面、書頁、書溝陰影、翻頁角、右緣六個分類書籤、紅緞帶）；`z2` 壓在右頁下緣的胡桃木托盤、鉛筆、羅勒、茶；`z3` 暗角。頁面內容、書籤文字、托盤裡的食譜都是介面疊層。
- **三步**（和舊前端的食譜庫選菜頁相同）：誰要吃 → 挑菜 → 結果。書上方的標籤顯示目前在哪一步。
  - **誰要吃**（左頁）：餐別、每位成員勾「一起吃／帶便當」。第一次存檔 `POST /meal-requests`（`mode: 'picker'`）後網址換成 `/pick/:id`；之後都是 `PUT { version, draft }`。
  - **挑菜**：左頁是條列清單，**一頁 10 道**，頁首可搜尋（菜名或食材），頁腳頁碼與翻頁。右頁是點到那道的標籤、食材與「為什麼不能選」。有禁忌食材的菜不能加；最多 10 道。
    食譜庫的端點不回每道菜的份量、時間、營養，所以右頁不顯示（頁面上有說明）；營養在下一步以整餐呈現。
  - **結果**：左頁是資料庫菜單（重新查詢、已換幾次、全家配方、避免重複的菜、已採用的提示）；右頁是整餐營養（缺值「未知」，三態：通過／超出或不足／計算不完整）。
    面板：每人營養、食材小知識（來源固定顯示）、送出生成（進度、取消、重新生成、服務狀態、T04 來源檢查；有結果時連到餐桌）。
- **書籤**：右緣標籤＝類型篩選（全部＋後端回的前四個類型＋「更多」）；「更多」開面板，四個面向（主食材、菜系、類型、主食種類）都在裡面，同一面向內是「或」、面向之間是「且」。
- **托盤**：壓在書上的紙鎮，顯示已選的菜與主要按鈕：挑菜時是「確定（n 道）」（存 `specified_dishes`、`dish_count` 與主食）；結果那一步是「不採用，換一份」（`POST …/menu-rejections`）與「採用這份菜單」（`POST /meal-plans`，帶 `recipe_ids`）。
- **沒有「拍冰箱」捷徑**：選菜流程送出的 `available_ingredient_ids` 固定是空的（舊前端也是），所以這裡不辨識食材。
- **唯讀**：生成中與已採用的單只能翻看；存檔遇到 409 `VERSION_CONFLICT` 時提供「重新讀取這張單」。完整問卷（非 picker）開到這裡會轉去 `/plan/:id`。
- **闔上**：點「闔上書」→ ②。
- **資料**：`GET/POST/PUT /meal-requests`、`GET …/recipe-catalog`、`GET …/recipes`、`POST …/nutrition-preview`、`POST …/knowledge-tips`、`POST …/menu-rejections`、`POST /meal-plans`、`POST …/submit`、`POST …/cancel`、`GET /jobs`、`POST …/t04-data`、`POST /sim-market/handoffs`。（`POST /assistant/recipes` 是飲食小幫手在用，這一景不用。）
- **手機**：兩個停靠點（左頁★／右頁與托盤），一次一頁。書籤在手機上看不到，左頁頁首多一排類型按鈕；物件列列出每個動作（含翻頁、上一步）。頁面內容本身可上下捲動。吉祥物在這一景站在右下角不跑（托盤上的主要按鈕就在跑道上）。

### 5.4 ③ 單板＋鍋 `/plan/:id`、`/plan/:id/cooking`

- **場景**：俯視流理台。「單板」是一塊夾著點菜單的木製寫字板（`PassBoard`）——從單軌取下的那張單夾在上面，問卷就寫在這張紙上；右邊是瓦斯爐的左爐口和同一口鍋的俯視（`PotTopView`）。從 ② 點空鍋進來是新單；點單軌的單進來時那張單飛到單板上，鍋裡已有前幾步的料。
- **分層**：`z0` 石紋檯面；`z1` 單板與金屬夾、點菜單（紙）、鉛筆、瓦斯爐（鑄鐵爐架、旋鈕）；`z2` 爐前一排備料碟（菜、菇、肉、配菜）與高湯壺——每完成一步，對應那一碟的料飛進鍋；`z3` 爐燈的光與暗角。鍋與問卷是介面疊層。
- **鍋的俯視圖**：由 `assets/pot/build_pot_top.py` 產生九張：`pot-top-0`（空鍋）、`-1`…`-5`（菜→菇→肉→湯→配菜補滿並亮起）、`-lidded`、`-ready`、`-failed`。
- **五步與鍋**（入鍋元素固定，與填寫內容無關）：

  | 步 | 單板內容 | 入鍋 | API |
  |---|---|---|---|
  | 1 | 日期、餐別、預算 | 🥬 菜 | `PUT /meal-requests/:id`（自動存草稿） |
  | 2 | 成員（頭像 chip，多選；可翻看個人目標） | 🍄 菇類 | `GET /members/options` |
  | 3 | **現有食材辨識**：相機框拍冰箱／檯面 → 辨識結果 chip 逐項確認，低信心加「?」，可手動補、可整步略過 | 🍗 肉 | `POST /recognitions`、`POST /recognitions/:id/confirm`、`POST /recognitions/:id/retry`、`DELETE /recognitions/:id` |
  | 4 | 主食偏好、不吃的食材（`IngredientPicker`） | 🍲 湯（湯底漲滿） | `GET /meal-requests/staple-options`、`GET /ingredients` |
  | 5 | 確認：摘要＋營養預覽；「開始煮」 | 🥚🍅🌽 配菜補滿、鍋全滿、鍋緣亮 | `POST …/nutrition-preview`、`POST …/submit` |

- **送出後（`/cooking`）**：鍋蓋蓋上、冒熱氣；紙留在單板上（顯示等了多久、取消、回看問卷）。鍋旁一列後端回報的真實階段：排隊中 → 查詢資料庫食譜 → 計算營養與價格 → 查詢營養知識 → 已完成；「AI 生成菜單中」「檢查菜單條件」「整理知識說明」只在後端回報時才列出，不假裝每次都有。輪詢 `GET /jobs?meal_request_id=&kind=meal_generation`（2 s；分頁在背景時暫停，和舊前端一樣）。
  （原設計的「單板滑回單軌」「料從備料碟飛進鍋」動畫還沒做。）
- **取消**：`POST …/cancel` → 掀蓋，料保留（草稿不丟），回單板第 5 步。
- **成功**：鍋蓋打開、整鍋全亮 → 鏡頭轉到 ④（只在 `/cooking` 看著鍋的時候；正在回看問卷就不打斷，只留一張「煮好了」的便條與連結）。
- **失敗**：鍋蓋半開冒黑煙，回到第 5 步顯示原因與「再煮一次」（重新 submit，換一把冪等鍵）。
- **驗證錯誤**：欄位層顯示；該步在單板步驟條標紅點；鍋不加料。
- **手機**：鍋在上半、問卷是下半的紙張抽屜（可下拉收起只留把手），一步一屏。這一景只有一個停靠點、沒有物件列；吉祥物在抽屜打開時收起。
- **其他房間帶過來**：`/plan/:id?step=N`（1–5，只對草稿有效）直接開在那一步；冰箱把手帶 `step=3`。食譜庫選菜的單（`mode: 'picker'`）開到這裡會轉去 `/pick/:id`。
- **第 5 步的資料庫菜單**：和舊前端一樣，確認頁有資料庫菜單預覽，可以直接採用（`POST /meal-plans` 帶 `recipe_ids`）或「不採用，換一份」（`POST …/menu-rejections`）；生成結果本身不在這裡，連到 ④。

### 5.5 ③b 鍋狀態機（`PotStateMachine`）

同一口鍋出現在：客廳門口（遠景）、廚房瓦斯爐（側視）、單板旁（俯視）。外觀統一火鍋，無主食。

| 態 | 外觀 | 對應 |
|---|---|---|
| 空鍋 | 湯底淡、無料 | 沒有進行中的問卷／工作 |
| 半滿 | 菜→菇→肉→湯 依已完成步數累加 | 草稿（`status` 草稿，依已填步數） |
| 全滿 | 配菜補滿、鍋緣亮 | 第 5 步待送出 |
| 蓋上冒煙 | 鍋蓋、蒸氣、階段列 | `queued`、`running` |
| 開蓋全亮 | 鍋蓋立起、鍋內光暈 | `succeeded`、待決定 |
| 失敗 | 鍋蓋半開、黑煙 | `failed` |

### 5.6 ④ 餐桌 `/plan/:id/result/:ver`

- **場景**：從正上方俯視餐桌（和食譜書、單板同一套俯視畫法）。圓桌在畫面正中，手機一屏看得到整桌。
- **分層**：`z0` 木地板、圓形編織地毯、盆栽、吊燈的光；`z1` 胡桃木圓桌與中央轉盤；`z2` 轉盤正中的小花瓶；`z3` 暖光與暗角。桌上其餘的東西都是依資料擺放的元件（`assets/tableware/`，由 `build_tableware.py` 產生）。
- **一桌菜**：餐單裡有幾道菜，轉盤上就擺幾個器皿，依類別：主食＝木飯桶（`dish-staple`）、海鮮＝橢圓盤（`dish-seafood`）、肉類＝圓盤（`dish-meat`）、蔬菜＝圓盤（`dish-vegetable`）、湯＝雙耳湯鍋（`dish-soup`）、其他＝小碟（`dish-other`）。4 道以內擺一圈，超過則縮小並排兩圈。菜的圖是「類別的代表圖」，不是每道食譜各畫一張。
- **座位**：每位成員一張椅子（`chair-top`）、一份餐墊（`place-setting`）、一個飯碗，沿桌緣等角度排開；成員數 1–8 都用同一套算法。
  - 點器皿 → 抬起到 `z3`，翻出做法與食材（`DishDetail`）。
- **每人飯碗**：飯碗＝該人營養判定（前端依「攝取 ÷（每日目標 × 這一餐的比例）」算的顯示規則；能不能採用仍只看後端的 eligibility）：熱量 ≤110%、蛋白質 ≥90% 三態徽章；缺值用空碗（`rice-bowl-unknown`）加虛線外框與「未知」，不畫飯。點碗 → 展開個人營養表（平面）。桌上另有家庭合計小立牌。
- **展開的面板**：桌機放在餐桌左右兩側的空位（左：個人營養；右：收據明細），不遮住桌子；手機改為從下方滑出的抽屜。
- **收據（`Receipt`）**：壓在菜盤邊。
  - 第一行「要買的整包」＝整包花費；第二行「這餐吃掉」＝按比例成本；兩行不相加。
  - 底部印章：`OK` 預算內／`BUDGET_EXCEEDED` 超出預算／`PRICE_INCOMPLETE` 價格不完整（不蓋章、列出未知項）。
  - 點收據 → 展開每項食材的包裝、單價、用量；價格未知的項目以虛線列出。
- **營養小知識**（`TipTray`）：桌上一個胡桃木小卡盤（`tableware/tip-tray.svg`）放著一疊知識卡，旁邊標「營養小知識 N 則」。
  - 資料：結果的 `knowledge.items[]`，每筆是一樣食材的 `ingredient_name`、`explanation` 與 `citations[]`（`attribution`、`source_url`）。食譜庫選菜流程則用 `POST …/knowledge-tips` 的 `tip_zh`。內容只照後端給的顯示，不改寫、不自行補充。
  - 展開：點卡盤 → 卡片攤開成一疊可左右翻的知識卡（桌機在餐桌左側面板、手機是下方抽屜）。每張卡：食材名、說明、來源；**來源固定顯示在卡片正面**並可點「原文」，不藏在翻面。
  - `status: 'available'`：卡盤有卡，標則數。
  - `status: 'unavailable'`：空卡盤（`tip-tray-empty.svg`）＋「小知識暫時拿不到」。面板寫明原因（服務暫時無法使用；`reason: 'BUDGET_EXHAUSTED'` 時寫本月外部服務額度不足），並說明菜單、份量與採用資格不受影響。`retry_available` 且尚未採用時顯示「只重試小知識」（`POST …/knowledge-retry`，不重新生成菜單，結果存成新版本）。
  - 重試中（`retries.knowledge` 為進行中）：標「小知識重試中…」，按鈕停用；成功後自動換到新版本，失敗顯示 `error.message`。
  - `status: 'not_found'`：空卡盤＋「這桌沒有小知識」，不顯示重試，也不拿其他內容充數。
  - 歷史快照：照當時存下的內容顯示，不提供重試。
- **手機**：單一停靠點；物件列列出每道菜、每位成員、收據、小提示；這一景不顯示底部分頁，最底下改為「採用這桌／換一桌」動作列。
- **動作列**（`z4`，手機固定底部），規則照舊前端的結果頁：
  - 採用這桌：`POST /meal-plans`（`meal_request_id`、`request_version`、`result_version`，帶冪等鍵）。採用後留在桌邊，顯示成功訊息，動作列換成「一鍵購入（有待買項目時）／回客廳／看紀錄」，不自動把鏡頭帶走。
  - 去決定／看原因：有 `pending_decisions` 時開狀態面板，逐項 `POST …/decisions`；決定和採用是兩件事，決定完還要後端判定可採用才能採用。
  - 換一桌：舊前端的「重新生成」——同一版問卷再 `POST …/submit`（新的冪等鍵），鏡頭回 ③ 的 `/cooking`。`POST …/menu-rejections` 只收 `{ version, recipe_ids }`、沒有原因欄位，而且屬於資料庫菜單流程（③ 第 5 步與 ②b），餐桌不用它。
  - 重新查價／重試小知識：`price-retry`、`knowledge-retry`；完成後換到新版本。上一次重試失敗後再按會換一把冪等鍵（同一把只會拿回同一個失敗的工作）。
  - 一鍵購入：採用後出現，`POST /sim-market/handoffs`。
- **歷史快照**（從 ⑤ 或廚房單軌進來）：同一場景但無動作列，狀態標「已採用」；不可改、不可重算。網址上的版本不是被採用的那一版時也只能看，並提供連到被採用版本與最新版本的連結。
- **資料**：`GET …/results`、`GET …/results/:ver`。

### 5.7 ⑤ 冰箱門 `/records`

- **場景**：正面近看冰箱門。門面刻意留白：**左半是「已採用」、右半是「營養與採購」**。桌機兩半同時看得到；手機一半就是一個停靠點。
- **分層**：`z0` 兩側露出的磁磚牆；`z1` 奶油色冰箱門、上方冷凍門下緣、鍍鉻把手、門面反光；`z2` 固定的裝飾磁鐵；`z3` 暗角。便利貼、月曆、圖表與它們的磁鐵都是介面疊層。
- **磁鐵＝分頁**：門上兩顆大磁鐵「已採用」「營養與採購」各標示一半；桌機上是標題，手機上點了等於換停靠點（同時更新 `?tab=`）。
- **已採用**：月曆（有餐盤貼紙的日子＝有採用餐單；多餐以貼紙數表示，最多畫三張）＋當日便利貼（各餐菜色、整餐熱量）。點日期換便利貼；點便利貼上的一餐 → 開唯讀的明細面板（價格、三大營養素、每道菜、每人營養、前一日比較、小知識與來源、一鍵購入）；由生成結果採用的那一餐另有「到餐桌看這一桌」連到 ④ 唯讀快照。網址 `?date=YYYY-MM-DD` 指定看哪一天。
- **營養與採購**：一張 CSS 長條圖（不用圖表套件），可切 7／30／90 天與「成本／熱量」；成本是每日**按比例成本**（趨勢端點不回整包花費，所以沒有「每週採購金額」圖；整包花費只在單餐明細裡），價格不完整的日子用虛線、未知的日子畫虛線「?」。下方是問卷清單（`GET /meal-requests`：日期、餐別、草稿版本、狀態），點了回到那張單。
- **把手**是可點物件：先確認，再 `POST /meal-requests { meal_date: 今天 }` 開一張新單 → ③ 第 3 步的相機框（`/plan/:id?step=3`）。
- **資料**：`GET /meal-plans`（日期清單、`?date=` 當日餐單）、`GET /meal-plans/trend`、`GET /meal-requests`、`POST /meal-requests`、`POST /sim-market/handoffs`。
- **手機**：兩個停靠點（已採用★／營養與採購）。物件列：月曆、當日餐單、一鍵購入（可以買的那幾餐）、拉開冰箱、趨勢圖、生成紀錄。

### 5.8 ⑥ 全家福 `/family`

- **場景**：回頭近看客廳牆上的畫。畫框裡的圖畫紙剛好是手機一屏的寬度。
- **分層**：`z0` 牆與畫燈的光；`z1` 黃銅畫燈、橡木畫框、襯紙、圖畫紙與蠟筆畫的背景（天空、太陽、雲、小房子、草地、花）、畫框下的黃銅名牌；`z2` 矮櫃檯面的盆栽、一盒蠟筆、相框與書；`z3` 失焦的窗簾邊與暗角。
- **人物＝成員**：`assets/family/` 的蠟筆人物（男、女、小孩、長輩四種，由 `build_crayon.py` 產生），依資料排在草地上，4 人以內一排、超過排兩排。蠟筆筆觸（粗邊、不均勻填色、略歪），名字、年齡、活動量；未填欄位用鉛筆底線「未填」，不猜值。這是除了吉祥物以外唯一不寫實的地方。
  - 點人物 → 左側面板顯示成員資料與每日基準（`GET /members/{id}/target`；後端回 422 算不出來的人，名字下方有鉛筆底線「目標算不出來」）；「編輯」在同一個面板換成表單（舊 `MemberFormDialog` 的九個欄位與驗證）。
  - 圖畫紙上的蠟筆標題「我們這一家」也可以點：開全家名單與統計（人數、份量合計、過敏與不吃的食材數）。
  - 人物圖：12 歲以下用小孩、65 歲以上用長輩，其餘依性別；最多畫 12 位，其餘從名單與物件列進入。
  - 虛線空位「畫上新成員」→ 新增。
  - 刪除需二次確認（橡皮擦動畫還沒做；確認時人物只是變淡）。
- **設定**：畫框下的黃銅名牌刻著家庭名稱，點它開設定：景深效果三段、家庭切換、服務狀態（`GET /health/team`）、登出（`POST /auth/logout`）。
- **面板**：桌機放在畫框左右的空牆（左：點到的成員資料與編輯、全家名單；右：設定）；手機改為下方抽屜。一次只開一個面板。
- **手機**：單一停靠點（span 620）；物件列列出每位成員、＋新成員、全家名單、設定。
- **資料**：`GET/POST/PUT/DELETE /members`、`GET /members/options`、`GET /members/{id}/target`、`GET /ingredients`、`GET /health/team`、`POST /auth/logout`。

### 5.9 飲食小幫手（浮動）

- **畫風**：吉祥物「小番茄主廚」（番茄身體、廚師帽、蒂頭、手腳）維持插畫風：平塗、圓潤、無材質，和寫實場景刻意區隔，一眼看得出它是「介面」不是「房間裡的東西」。原始檔 `src/assets/mascot/mascot.svg`，可動部位以 class 標記（雙腳、雙手、身體、影子）。
- **跑動**：在畫面最底部的一條跑道上左右來回跑（`z4`），到邊緣轉身；跑步循環 0.4 s（雙腳交替、雙手擺動、身體上下彈、影子縮放）。偶爾停下來看向指標或最近一個可點物件。只有吉祥物本體可點，跑道其餘區域不擋場景的點擊。手機上跑道在底部分頁上方。
- **聊天室**：點吉祥物 → 它停下、轉身揮手，身旁彈出**懸浮視窗**（桌機約 27% 寬、手機約 90% 寬，底部有指向吉祥物的小尖角）；視窗可拖曳、可縮小回吉祥物、可展開成 `/assistant` 全頁。關閉後吉祥物繼續跑。
- **未登入**（大門、玄關）：吉祥物照跑但只是裝飾，點了冒出一句「開門後就能問我」。
- **內容**：回答附參考來源卡（標題、站名、連結）；不診斷、不處方、不給劑量（沿用 R14 與後端回應）。景深效果切換在右上角的家庭選單與全家福的設定裡（視窗裡不重複放）。
- **景深模式**：靜態景深與系統減少動態時不跑，站在右下角；關閉模式同樣固定。
- API：現有 `assistant.ts` 端點。

## 7. 系統架構

### 7.1 技術選型

| 層 | 選擇 | 理由 |
|---|---|---|
| 建置 | Vite 8 + React 19 + TypeScript 6 | 與 `frontend/` 一致 |
| 路由 | React Router 8（data router） | 舊路由轉址；路由＝停靠點 |
| 伺服器狀態 | TanStack Query 5 | 沿用 query key 與輪詢 |

| 無障礙原語 | Radix UI（Dialog、Tabs、Toggle Group） | 鍵盤與讀屏，不帶樣式 |

### 7.3 景深與鏡頭引擎

```
DepthProvider
 ├─ mode: 'immersive' | 'static' | 'off'      (localStorage: depth-mode)
 ├─ pointer: MotionValue<x,y> ∈ [-1,1]         (pointermove，rAF 節流)
 ├─ gyro: MotionValue<β,γ>                     (DeviceOrientation，首次點擊授權)
 └─ useDepth()

Camera
 ├─ stops.ts: { id, room, origin:{x,y,scale}, tilt, enterFrom[] }
 ├─ rooms/*/hotspots.ts: { id, label, stop, bounds, status(), action() }  ← Hotspot、HotspotDock、讀屏清單共用同一份
 ├─ 手機：每房間 1–3 個 phoneStops；滑動一次換一個，物件列點擊 → 轉到 hotspot.stop
 ├─ 路由變化 → 查轉場表 → 同房間 400ms / 跨房間 600ms（+blur）
 ├─ 把 origin 套到 <Room> 的 transform；pointer/gyro 疊加 ±4–6°
 └─ static：直接跳到 origin 並淡入；off：不掛 Camera

<Room>   perspective 1200px（手機 900px）、preserve-3d，包住五個 <Layer>
<Layer>  視差係數 × pointer → translate3d；static 只輸出固定 translateZ
<Hotspot> 可點物件：hover/focus 上浮到 z3、放大 1.03、亮邊；role=button、aria-label
```

- 只動 `transform` 與 `opacity`；`will-change` 只在轉場與互動中加上。
- 同時活動的視差層 ≤ 12；不可見的房間卸載。
- 同一口鍋在不同場景用 `layoutId="pot"`，跨場景轉場時形狀連續。
- 鍋狀態由一個 selector 從 `meal-request` + `job` 推導，三個視角共用。

### 7.4 資料流

```
元件 ──useQuery/useMutation──▶ api/*.ts ──axios /api──▶ Vite proxy | Caddy ──▶ backend:8000

新的一餐：點空鍋 → POST /meal-requests → /plan/:id
問卷：每步 PUT /meal-requests/:id（自動存草稿）
第 3 步：POST /recognitions → confirm → 寫入草稿的現有食材
送出：POST …/submit → /plan/:id/cooking → 輪詢 job
成功：succeeded → /plan/:id/result/:ver
採用：POST …/decisions → POST /meal-plans → /today
```

- Query key 沿用 `frontend/`：`['me']`、`['meal-requests']`、`['meal-request', id]`、`['results', id]`、`['meal-plans', range]`、`['jobs']`。
- 鍋狀態 selector：`potState(request, job): 'empty'|'filling'|'full'|'cooking'|'ready'|'failed'`，`filling` 帶已完成步數。
- 未知值型別保持 `number | null`，元件層統一 `UnknownValue`。
- 不新增後端 API。

### 7.5 部署與並存

- 開發：`frontend-3d` 使用 5174 埠，proxy 目標同 `VITE_API_PROXY_TARGET`；`/api/admin` 阻擋與 `frontend/` 相同。
- Compose：新增 `frontend-3d` 服務（profile `preview`，預設不啟用），Caddy 規則同 `frontend/`（阻擋 `/api/admin`、`/api/internal`）。
- 切換：驗收通過後對外網址指向 `frontend-3d`，舊 `frontend/` 保留一個版本週期。
