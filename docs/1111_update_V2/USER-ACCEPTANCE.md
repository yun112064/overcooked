# V2 使用者親自驗收

本頁是待你操作的驗收清單，不是人工驗收完成報告。現有 HTTP 自動驗證已跑通資料庫菜單→採用→Sim→Admin，真 AI 也已生成可採用結果；你的完整瀏覽器操作仍需逐項確認。證據見 [驗證紀錄](../1102_V3/VALIDATION.md) 與 [AI 身分驗證](AI-IDENTITY-VALIDATION.md)。

## 入口與帳號

| 入口 | 用途 |
| --- | --- |
| [主站](http://localhost:8240) | 家庭、問卷、照片、生成、採用、歷史、小幫手 |
| [Sim 超市](http://127.0.0.1:8241) | 從主站有效採用結果帶入採購，再模擬結帳 |
| [Admin](http://127.0.0.1:8242) | 查看確認事件、來源與管理流程 |

Admin 使用已設好的**同一個驗收管理帳號**登入，不必逐角色換帳號，也不要重新註冊。帳密以本機私密交接為準；Git 文件不存帳密。該帳號已核對 12 個角色、34 個權限，臨時 operator 授權已撤銷。擁有全部角色仍不能自行審核／發布自己提出的變更，這項限制保留。若要測試需要另一審核者的流程，安排獨立審核者，不要把正常拒絕當成缺權限。

主站一般驗收帳號使用本機既有帳號與家庭。這次所有操作僅限 V2 隔離庫；不要切到其他舊入口或正式服務。無法連線時先請執行者確認服務，不要直接用根目錄 compose 啟動另一套資料庫。

也可從主站自行註冊你的驗收帳號、建立家庭與成員；這樣個人操作紀錄可與工程測試家庭分開。Admin 繼續使用原同一管理帳號。

## 建議先走一次完整主流程

1. 主站登入，進成員管理，確認至少一位成員的年齡、體重、活動及用餐份量。先挑一位參加本餐，降低第一次結果比較的複雜度。
2. 新建今天晚餐，預算 1000、一道菜、指定「簡單蒜頭雞(電鍋版)」、已有食材選雞腿肉，主食選「不需要主食」。這是已跑通的真來源案例；R0036 在來源 SQL 和工作簿都標「主食」，目前沒有核准修正，不要另外加飯後把分類衝突當作生成服務故障。
3. 預覽並記下食材、營養、缺買項與成本，再正式生成。應看到工作狀態到結果，資料庫菜單使用同份來源。知識說明可能顯示不可用，不能把沒有證據的文字當成功。
4. 閱讀結果後按採用。僅預覽／生成不會建立採用歷史。確認能在歷史找回本餐與採用時快照。
5. 從該採用結果開啟 Sim，核對缺買清單、商品包裝及整包實付；完成模擬結帳，記下訂單。重新開同筆收據應保留，不應重複產生訂單。
6. Admin 同一帳號登入，找到同筆餐單確認流程，核對 confirmed、snapshot_saved、history_saved、ingredients_saved、nutrition_saved、cost_saved 及 sim_checkout_confirmed。比對餐單／訂單識別，不能只看總事件數。

已實測案例的包裝報價為 99 元；你操作時若有新真實報價，按顯示的時間、商品與來源核對，不把 99 元寫死成通過條件。現有雞腿只是使用者聲明已有食材，不是合成營養或商品來源。

在每項旁自行記「通過／未通過／未做」、畫面時間與問卷／工作／餐單識別；沒有操作的項目保持未做。

| 項目 | 你要做的動作 | 預期可觀察結果 |
| --- | --- | --- |
| T01 食譜 | 開食譜選擇與詳情，檢視真食材、步驟、來源；另看特殊 batch／950 份食譜。 | 食譜不是展示資料；batch 和份數不混用，不以同名 Excel 覆蓋來源。 |

| T03 目標 | 改用餐成員／份量再預覽，核對逐人目標及總量。 | 目標依成員改變且有規則版本；未填必要欄位要提示。 |
| T04 營養來源 | 打開營養／來源詳情，查看可算與缺來源食材。 | 有可追溯來源；未知不填0；補資料不直接變成已核准對照。 |
| T05 模型 | 問卷照片辨識上傳真照片，可先用 `data/recipe_pic/R0010_pic_01.jpg`。 | 有辨識結果或清楚無結果／失敗狀態；這只驗功能，不代表整體模型品質達標。 |
| T06 服務 | 請執行者展示 V2 健康／版本檢查與一次受控重啟，再重新登入讀同筆資料。 | 資料保留、標配依賴狀態明確；不能用程序存活代替真依賴可用。 |
| T07 身分 | 登入、選家庭、增修成員；跨家庭權限由執行者配合第二測試家庭驗證。 | 自己資料可操作；別人家庭資料不可讀寫。 |
| T08 問卷 | 填日期餐別、過敏忌口、指定菜、已有食材，保存後離開再回來修改。 | 草稿可恢復，生成使用提交時版本；錯誤欄位有提示。 |
| T09 照片確認 | 檢查照片建議，從標準食材候選確認或手動修正，再回問卷。 | 未確認前不直接當已有食材；不把 YOLO label 猜成 FOOD_ID。 |
| T10 工作 | 提交一次生成，查看進度／結果；請執行者展示相同 key 重送、重啟恢復及配額紀錄。 | 不重複工作／扣費；失敗保留問卷。避免用連續手動點擊製造不必要付費。 |
| T11 檢索／知識 | 查看預覽與正式菜單的檢索結果、來源及知識說明。 | 忌口／歷史排除生效；無合格證據顯示不足，不編造營養理由。 |
| T12 計算 | 同菜、同份量比較預覽及正式營養，查看每人分配與主食。 | 兩路一致；熱量≤目標110%、蛋白質≥90%，不是兩項都±10%。 |
| T13 成本 | 比較缺買用量、比例成本、整包實付，另查看缺價情況。 | 已有食材不重買；未知／不可換算有提示，不當免費。 |
| T14 AI | 另建「蒜香清蒸雞胸肉」案例，分別以已有雞胸、已有雞腿測兩種情境，再生成。 | AI 結果標記清楚；雞胸為 FOOD001564，不能把已有雞腿 FOOD001578 當雞胸。真生成會經 T10 計費；已有兩筆可供先看，尚未替你採用。 |
| T15 決策 | 分別查看、拒絕、重新生成及採用；遇價格例外先讀提示再選擇。 | 各動作狀態清楚；不同結果版本不混用，查看不等於採用。 |
| T16 歷史 | 按下一節完成兩日期採用、翌日排除、歷史及 Sim／Admin 核對。 | 可查兩天快照，前日已採用菜被排除；指定例外只影響指定菜。 |

## 兩日歷史不可省略

- 使用兩個相鄰日曆日期 D−1 與 D，不必真的等待一天。在 D−1 採用真菜單，記下菜名與餐單；D 再生成時不指定同菜，確認前日各餐已採用菜排除。
- 在 D 明確指定前日其中一道菜，確認只豁免該指定菜。另測同日其他餐別排除；僅查看／拒絕的菜單不應算已採用。
- 兩日期都打開歷史，核對來源版本、營養、成本、AI 標記；請執行者配合測採用前歷史變更、重送、跨家庭及發布／回復後快照不變。這些工程檢查不能單靠畫面推定通過。
- 最後從其中有效採用餐單走 Sim 與 Admin。代理已在 V2 實際跑過 11/11、11/12 真 R0036 的兩日 HTTP 流程：前日排除／指定例外、改版舊結果拒絕、同鍵採用與 Admin 六事件不增加、歷史／趨勢、跨家庭拒絕；另已查證新真報價 snapshot 10 寫入後，兩筆歷史快照仍引用 snapshot 7 且雜湊不變。詳見 [T15／T16 HTTP 紀錄](T15-T16-HTTP-VALIDATION.md)。這是工程準備檢查，你的畫面驗收仍未做；來源／管理價格政策發布或回復後快照不變、歷史競態與不同餐別去重仍待驗。

## 三項標配與目前限制

本輪測 YOLO 與小幫手，T11 依使用者指示暫緩。小幫手從主站「飲食小幫手」進入，先問一般食物問題，核對串流結束與可開啟的引用，再問資料不足問題；應說明不足，不能編來源。模型慢或服務不可用要留下實際狀態，不以舊分支成功紀錄代替本次測試。

- 四項 recipe-derived-only 食材 `FOOD000312`、`FOOD000808`、`FOOD001170`、`FOOD001682` 仍是來源缺口基線；不能把未知營養補0使菜單過關。
- T11 最新真 AI 成功案例的知識解說仍 unavailable。檢索／索引存在不等於已有合格 nutrition_fact 與逐字 evidence_quote。
- YOLO 現有整體 precision／recall 不足以證明指定類別品質門檻；真照片能辨識與品質驗收是兩回事。
- 最終 AI prompt v9／schema v5 已真生成兩次成功並取得 adoptable=true，尚未採用這兩筆；不代表 AI 採用→Sim→Admin 已全通。
- 全角色帳號已驗證，不代表每個管理發布／回復流程已驗證。乾淨機安裝、標配整體容量、完整兩日及你的人工操作未完成前，不能宣告整專案驗收通過。

驗收完交回每項結果與失敗步驟即可；保留出錯頁與工作識別，不需要貼密碼、API key 或完整私密日誌。
